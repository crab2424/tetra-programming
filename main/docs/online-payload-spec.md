## 0. 大前提（これを外すと全部ずれる）

- **方式 = B（ライブ状態ストリーミング）**。各クライアントが自分の権威ゲームをローカル完結で実行し、状態を相手へ流す。受信側は相手ミニ盤面に **描画するだけ**（再シミュレーションしない＝デシンク原理的に起きない）。
- **自分の操作は client-authoritative**＝ネット遅延ゼロ。50msの遅延予算は「おじゃま伝達」と「相手盤面表示」にだけ充てる。
- **サーバー（tetra-server）は対戦中フレームの中身を解釈しない**。`0x06 GameEvent`（reliable）/`0x07 PieceState`（unreliable）を受けたら相手の同種チャンネルへ**素通し中継**するのみ。したがって対戦中の値の意味づけ（サブプロトコル）は **Rust を変更せずに改訂できる**。
- **逆に、サーバーが発番・調停すべきもの**（ルーム/マッチング/開始タイミングの権威化など）は JSON 層（`payload/json.rs`）で扱う。

### 通信の3層 と 管理場所

| 層 | 物理 | 管理場所（定義の真実の源） | 役割 |
|---|---|---|---|
| **A. シグナリング** | WebSocket | `tetra-server/src/signaling.rs` | SDP/ICE 交換のみ。ゲーム値は流さない |
| **B. JSON制御層** | WebRTC reliable（`0x03/0x04` でラップ） | `tetra-server/src/payload/json.rs`（`JsonMessage` enum） | ルーム/マッチング/通知。**サーバーが解釈・調停する** |
| **C. 対戦サブプロトコル** | WebRTC reliable / unreliable | 新実装で定義（旧プロトタイプは internal-subprotocol.md ＋ コーデック1ファイル） | 対戦中のゲーム状態。**サーバーは素通し** |

> **設計原則（言語に依らず維持すべき点）**: C層のエンコード/デコード（コーデック）は **クライアント2者が完全に同一のバイト解釈** を持つ必要がある。TS実装では**1つの型定義/コーデックモジュールを単一の真実の源**にし、両者が同じものを使う（旧JSは「本体」と「testclient」で同一ファイルを verbatim 複製していた＝二重管理で事故りやすかった。新実装では共有パッケージ化を推奨）。サーバーは中身を解釈しないので、C層の改訂にRust変更は不要。

## 3. 「対戦設定（マージン/火力/おじゃまレート等）」の合意 ★Issue #4 に未記載だが必須

VS設定（`main/src/config/vs_settings.js`）は**両クライアントの権威エンジンの計算に直接効く**。両者で値が食い違うと攻撃力やせり上がりがずれ、対戦が不公平・不整合になる。

| 設定キー | 既定 | 効く対象 | 危険性 |
|---|---|---|---|
| `all.marginTime` | 96 | 火力の時間倍率（§4.1） | **最重要**。タイマーと直結 |
| `all.attackBias[player/cpu]` | 0 | 火力補正の乗率 | 食い違うと火力非対称 |
| `tet.holdEnabled` | true | ホールド可否 | |
| `tet.garbageHoleRate` | 70 | おじゃま穴率（テト） | 穴は送信側が確定するので表示は揃うが、設定UIは合わせるべき |
| `tet.garbageDamageOnClear` | true | 消し時のダメージ挙動 | |
| `puyo.ojamaRate` | 70 | おじゃま換算レート（ぷよ） | 食い違うと火力非対称 |

**方針（要・共同開発者と合意）**: これらは「ホストが決めた設定を両者に配る（ホスト権威）」のが堅い。
配送経路の案: 開始ハンドシェイク（Ready 合意付近 or JSON層の開始通知）に **設定スナップショットを1回だけ載せて両者が同じ値で適用する**。設定同期は **(a) JSON層に「対戦開始設定」メッセージを足す**か、**(b) サブプロトコルに設定ブロックを足す**かのどちらか。サーバー調停を将来のランク戦で効かせたいなら **(a) JSON層（サーバー権威）推奨**。

## 4. 特に注意すべき4論点

### 4-1. タイマー系（マージン含む）★

**問題の核心**: マージンタイムは「ゲーム開始からの経過時間」で火力倍率（`vsMarginMultiplier`、`puyo/ojama.js:281,467` で攻撃に乗る）をランプさせる。各クライアントは**自分のローカル時計**で倍率を計算する。したがって —

1. **開始時刻が両者でずれると、同じ瞬間でもマージン倍率が異なる**。
   - 旧プロトタイプの開始同期は「両者 READY が揃ったら各自カウントダウン開始」＝**ずれ ≒ 片道遅延**（数十ms）。秒オーダーのマージンに対しては実用上許容だが、新実装では **サーバー権威の `startAt`（絶対時刻 or 共通基準）を JSON層で配る**方を推奨（Issue #4「ラウンド開始通知」をサーバー発番にする案）。
2. **マージンは送信側で確定して送る**＝受信側はマージンを再計算しない。`GarbageSend 0x04` の `amount` は**送信側がマージン倍率まで適用した最終火力**。これにより「受信側が自分の時計でマージンを掛け直して二重適用」を防ぐ。→ **この原則を崩さないこと**（受信側は amount をそのまま予告へ積むだけ）。
3. **マージン設定値そのものの一致**: `marginTime`（負値=事前経過を含む）が両者で違うと、各自の倍率カーブが違う＝非対称。§3 の設定同期で揃える。
4. **`t:u32`（GameStart相対ms）の基準**: 全 GameEvent/PieceState の `t` は「自分の GameStart からの相対ms」。受信側は初回到着で `offset = localArrival − t` を確定し以後 `t+offset+buffer` で再生。**この `t` は表示再生用であって、マージン倍率の計算には使わない**（倍率は各自のローカル経過時間）。混同禁止。

> まとめ: **タイマーはローカル駆動・マージン火力は送信側で確定済みで送る**。同期すべきは「開始の足並み」と「マージン設定値」の2つ。

### 4-2. NEXT（puyo・tet 両方そろえる）★

**2つの独立した要求があるので分けて考える。**

(A) **表示としての相手NEXT** = `Spawn 0x01` に NEXT列を載せて相手パペットへ描く（表示同期）。
- テト: `next:u8×nextCount`／ぷよ: `next:(pivot,child)×nextCount`。

(B) **同ツモ（両者が同じツモ順）** = 公平性の設計選択。**共有seed**で実現する。
- Control `0x08` READY の `seed`（各自が乱数生成）を**両者でXOR**して共有シードを得る（0なら1）。
- 共有シードを **ツモ専用乱数 `tumoRng`** に注入する（**おじゃま乱数とは分離**＝受信おじゃま量が違ってもツモ列はずれない）。
  - テト: `getNextType`（`board.js`）が `this.tumoRng || Math.random`。
  - ぷよ: `_tumoRandom()`（`tumoRng ? tumoRng() : _random()`）経由で `_makePair`/`_initNextQueue`/`_initActiveColors`。
- **オフライン挙動は不変**（`tumoRng` 未設定でフォールバック）。
- **stale seed 対策**: 使い回す versus インスタンスに seed が残ると CPU戦まで決定論化する → CPU開始/退出で `tumoRng=null` にリセット必須。

(C) **カウントダウン中の相手NEXT表示**（既知の落とし穴）:
- カウントダウン直前に「**NEXTだけ**」を送る（現在ミノ欄に sentinel: テト`type=0xFF`/ぷよ`pivot=child=0`）。受信側は盤面を空のまま NEXT だけ反映。本物の初手 Spawn で盤面に初手が出て NEXT が1シフト。
- **初回試合のみ受信側 `initGame` のアセット読込が遅く取りこぼす** → カウントダウン中に複数回再送（冪等）。**根治はロードタイミング §4-4**。

> まとめ: NEXTは「表示=Spawnに載せる」「同ツモ=共有seed＋tumoRng（おじゃま乱数と分離）」「開始直前はsentinelでNEXTだけ先送り」の3点をテト/ぷよ両方で揃える。

### 4-3. おじゃま系 ★

**Issue #4 の指摘「送信/受信ではなく通知（全員共有）」への回答**: 攻撃側が**火力 `amount` ＋ 穴パターン `holes` まで確定**して `GarbageSend 0x04`（**reliable**・欠落不可）で送る。

- **穴を送るので共有RNG不要**: 受信側は自分で穴をランダム生成しない（＝両者の穴が一致）。なお受信側エンジンは `applyGarbage`/`_generateOjama` で穴を再計算する実装だが、**せり上がり結果が決定的なら送信穴値は無害**（既存仕様）。新規に整合させる場合は「送信穴を受信側がそのまま使う」方が安全＝要確認ポイント。
- **火力はマージン適用済み**（§4-1）。受信側は予告キューに積むだけ。相殺・着弾判定は受信側の既存ロジック（`tet/garbage.js`・`puyo/ojama.js`）。
- **着弾（ready化）タイミング**: オンラインは送り手の「連鎖完了/確定」信号が直接来ないので、以下で代替（既知バグ⑤の確定版）:
  - **ぷよ受け手**: 受信直後は `{ready:false, internal:false}` で**予告だけ即表示**（降下不可）。`ready` 化は「**相手の次ツモ出現（Spawn 受信）**」を合図に `delay≈800ms` 後（＝相手の連鎖が完全に終わった確証）。
  - **テト受け手**: 連鎖が無いので受信後 `delay`（送り手ぷよ=1000ms/送り手テト=1500ms）の個別タイマーで ready 化。
  - **ぷよの予告表示/降下可は別軸**: 表示は `internal`、降下可否は `ready` で決まる（`_updateOjamaYokoku` は internal依存）。混同禁止。
- **予告ゲージの可視化**: 各自が自分の garbageQueue の ready/unready 段数を `PendingUpdate 0x06` で相手へ送り、相手パペットのゲージに描く（「相手に降りかかっている火力」が見える）。これは表示同期で、おじゃま本体（`0x04`）とは別物。

> まとめ: おじゃまは**reliableで火力＋穴を確定送信**（通知＝両者同情報）。**マージンは送信側で適用済み**、**ready化は相手Spawnを合図に遅延**、**予告表示(internal)と降下可(ready)は別軸**。

### 4-4. ロードタイミング ★

**問題**: 対戦開始時、受信側の `initGame`（特に**ぷよの画像読込** `_loadImages`）が初回だけ遅い。その間 net リスナ（`_wireNet`）が未接続で、開始直前に送られる初期NEXT（§4-2 C）等を**取りこぼす**。実機で「初回試合のみ約500ms 相手NEXTが古い」が残る。

**対策の階層**:
1. **暫定（旧プロトタイプで採った対処）**: カウントダウン中に初期NEXTを密な間隔 `[120,280,500,900,1500,2200]ms` で再送（冪等）。floor 直後に届かせる。対症療法。
2. **根治（未実装・ユーザー要望 ⑫）**: **ロビー段（online入室 or 2人在室時）の idle で puyo 画像を warm**しておく。`PuyoGame._sharedImagesLoaded` が立てば2回目以降の `initGame` は即時化（`lifecycle.js:332`）＝初回のみ問題の根を断つ。テト側は画像読込が無い/軽いので主にぷよ対象。
3. **設計原則**: **net リスナの接続を `initGame`（重い初期化）より前に張る**。リスナさえ生きていれば、重い読込中に来たイベントもバッファ/適用できる。開始ハンドシェイク（READY→カウントダウン）は「両者の重い初期化が完了してから」進めるのが理想 → ここを**サーバー権威の開始通知（§4-1）に寄せる**と「両者ロード完了を待って startAt を配る」が自然に書ける。

> まとめ: ロードは「**リスナ先・初期化後**」「カウントダウン中の冪等再送」で凌ぎ、根治は**ロビー段でのアセット先読み**＋**両者ロード完了を待つサーバー権威の開始通知**。

## 5. 管理場所まとめ（誰がどこを直すか）

> 新実装（TS+Rust）での責務分担の指針。ファイルパスは確定後に埋める。

| 変更したいもの | 担当（層） | サーバー再ビルド要否 |
|---|---|---|
| ルーム/マッチング/在室通知/**開始通知のサーバー権威化**/**設定スナップショット配送(JSON案)** | B層・Rust サーバー（JSON payload・ルーム管理） | **要**（再ビルド/再デプロイ） |
| 対戦中の値（NEXT/盤面/おじゃま/SE/連鎖/開始合意 等のバイト設計） | C層・**共有コーデック**（TS型定義＋エンコーダ） | **不要**（サーバーは素通し） |
| 送信フック（エンジンのどこで値を出すか） | クライアント・ゲームエンジン側（tet/puyo） | 不要 |
| 受信反映/パペット描画/着弾タイミング/ロード | クライアント・オンライン制御層 | 不要 |
| VS設定（マージン/火力/おじゃまレート）の定義と同期 | クライアント設定 ＋（同期方式によりB層） | 同期をJSON層に載せるなら要 |
